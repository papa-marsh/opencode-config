# Maestro Standalone Library

Rearchitect maestro from a monolithic Docker app into an installable Python library. A user installs the package, writes a small `app.py`, and gets everything today's `maestro/app.py` does:

```python
from maestro import MaestroApp

app = MaestroApp(hass_url=..., hass_token=..., redis_host=..., redis_port=..., ...)
```

This is a green-field rebuild, not a live migration. Two new repos:

- **`hass-maestro`** (final name TBD): the library. Seeded from the current `~/Repositories/maestro` framework package.
- **`maestro-scripts`**: the user application. Seeded from the current `~/Repositories/maestro/scripts` subrepo. Becomes a proper standalone app that depends on the library, and serves as the reference consumer.

PyPI publication is deferred; the architecture below is the prerequisite. Until then, maestro-scripts consumes the library via a git or path dependency.

## Decisions Already Made

- Constructor-driven: all initialization happens inside `MaestroApp.__init__`. No import-time construction anywhere in the library.
- `MaestroApp` subclasses Flask (stays directly servable by gunicorn as `app:app`).
- User-facing config is flat constructor kwargs. No requirement that users use env vars; that is their `app.py`'s business.
- DB is optional (`db_url=None` skips SQLAlchemy setup). Redis stays required: it backs the state cache, entity locks, and the APScheduler job store.
- Registry is generated into the user's project (`registry_dir`), imported as `from registry import ...`.
- Custom domains live in the user's project (`custom_domains_dir`); the wildcard graft into `maestro.domains` is removed.
- All maestro Redis keys are namespaced under a configurable prefix (default `maestro:`).
- Shell mode detection is replaced by an explicit `background_services=False` flag. `@app.shell_context_processor` still works since MaestroApp is a Flask.
- The `mt` pytest fixture ships as a pytest plugin entry point so consumers get it without conftest wiring.
- Shell config/preloads are the user's responsibility, not the library's.

## Target User Project Layout (maestro-scripts)

```
maestro-scripts/
  app.py                # entrypoint: constructs MaestroApp; gunicorn "app:app"
  registry/             # generated by RegistryManager, user-owned (committed or gitignored, user's call)
  custom_domains/       # optional Entity subclass extensions
  scripts/              # automation modules, loaded at startup
  conftest.py           # minimal; mt fixture comes from the library's pytest plugin
  pyproject.toml        # depends on the maestro library; owns catt, gunicorn, psycopg, etc.
  Dockerfile / justfile # deployment, migrated from current repo
```

## Constructor API

```python
app = MaestroApp(
    hass_url=...,                     # required
    hass_token=...,                   # required
    redis_host=..., redis_port=...,   # required
    db_url=None,                      # optional; None = no DB
    scripts_dir=Path("scripts"),
    registry_dir=Path("registry"),
    custom_domains_dir=None,          # optional
    redis_key_prefix="maestro",
    timezone="America/New_York",
    background_services=True,         # False = no websocket/scheduler (REPL/shell use)
    configure_logging=True,           # False = host owns logging config
    autopopulate_registry=False,
    domain_ignore_list=(),
    notify_action_mappings={},        # plus remaining notif settings from config.py
)
```

Init sequence inside the constructor (the future-state equivalent of today's import-time bootstrap):

1. Build internal `MaestroConfig` from kwargs; register as the global config.
2. Register self as the current app (`get_app()`); double-construction raises.
3. Configure logging (unless opted out).
4. `db.init_app(self)` if `db_url` provided.
5. Put project paths on `sys.path`; import custom domains module if configured.
6. `load_script_modules(scripts_dir)`: imports trigger decorators, registry modules, DB models.
7. If `background_services`: start scheduler (RedisJobStore), register cron/sun jobs, start WebSocketManager, fire `MaestroEvent.STARTUP`, register atexit shutdown.

## Coupling Inventory and Resolutions

### 1. Import-time env config

`maestro/config.py` reads env vars at import; 12 modules value-import from it (`app.py`, `utils/push.py`, `handlers/state_changed.py`, `testing/maestro_test.py`, `utils/dates.py`, `utils/internal.py`, `domains/person.py`, `integrations/redis.py`, `triggers/sun.py`, `triggers/cron.py`, `integrations/home_assistant/client.py`, `integrations/home_assistant/websocket_client.py`, `integrations/state_manager.py`). Values freeze during `import maestro`, before the constructor can run.

**Resolution:** `MaestroConfig` frozen dataclass, populated by the constructor, exposed via `get_config()`. It is internal plumbing for constructor kwargs, not a user-facing type (though the constructor may accept one for programmatic use). All 12 modules switch from value imports to `get_config().x` reads at call time. `get_config()` before construction raises a clear "MaestroApp has not been constructed" error. No `from_env()` needed; users read env vars themselves.

Watch for hidden import-time reads during the port: module-level constants derived from config, default parameter values, and class attributes (see item 6).

### 2. Import-time singletons and side effects

Today `maestro/app.py` runs `configure_logging()`, creates `db`, and constructs the entire app as a side effect of import. Test/shell mode sniffing exists only because import-time construction forced it.

**Resolution:**

- `MaestroApp(Flask)` with the explicit init sequence above.
- `db = SQLAlchemy()` stays module-level in `maestro/__init__.py`. Creating the extension object is side-effect-free and must happen at import so user model files can do `class X(db.Model)` before the app exists. Two-phase init: constructor calls `db.init_app(self)` only when `db_url` is set. A user touching `db.session` without `db_url` gets flask-sqlalchemy's own "not initialized" error, which is accurate.
- Internal lazy `from maestro.app import app` sites (`triggers/cron.py`, `triggers/sun.py`, `integrations/home_assistant/websocket_manager.py`, `utils/scheduler.py`) become `get_app()`.
- Constructor test-mode branch is deleted: tests never construct `MaestroApp` (the `mt` fixture builds its own lightweight Flask app). The pytest sniffing inside `StateManager` / `invoke_funcs_threaded` / `JobScheduler` is kept; it is pragmatic and works for consumers.
- Shell-mode sniffing is deleted in favor of `background_services=False`.

### 3. Registry generation in user space

`RegistryManager.registry_dir` is hardcoded to `/maestro/registry` (inside the installed package; unwritable and wrong for a pip install).

**Resolution:** `registry_dir` comes from config. Generated modules live in the user project and are imported as `from registry.light import bedroom` (project root is on `sys.path`). The `REGISTERED:` Redis cache-key mechanism and `prune()` are unchanged. The generated-file header should point at library docs instead of `maestro/registry/README.md`. The ruff per-file-ignores for generated code (`E501`, `F401`, `I001`) move to maestro-scripts' pyproject under `registry/**.py`.

### 4. Custom domains

`maestro/domains/__init__.py` does `from scripts.custom_domains import *`, a library-imports-user-code inversion. It exists solely so generated registry modules can write `from maestro.domains import Thermostat` for custom parent classes (single import namespace, `RegistryManager._write_module` line 216).

**Resolution:** the wildcard import is deleted. `custom_domains_dir` config param; maestro derives the import name from the directory name and ensures importability. The generator emits two import groups: `hasattr(maestro.domains, class_name)` decides whether a parent imports from `maestro.domains` or from the custom domains module:

```python
from maestro.domains import Light
from custom_domains import Thermostat
```

User scripts import custom domains directly (`from custom_domains import Thermostat`): user code importing user code. Nothing else in core touches custom domain classes; StateManager, triggers, and handlers operate on `Entity` generically. The existing parent-class preservation in `update_existing_module` / `prune` keeps working since it parses class names from the generated files.

Note this must be a constructor param, not a post-init method: script loading (which imports registry modules, which import custom domains) happens inside the constructor.

### 5. Script loading

`load_script_modules()` hardcodes `/code/scripts` with a CWD fallback.

**Resolution:** `load_script_modules(scripts_dir)` from config. Import naming (top-level `family.ellie` vs `scripts.family.ellie`) is an open decision; default to preserving today's behavior (scripts_dir itself on `sys.path`, top-level module names). `TriggerManager` line 76 (`module.removeprefix("scripts.")`) is adjusted to match whatever is chosen.

### 6. Redis key namespacing

Maestro shares the user's Redis; keys could collide with theirs.

**Resolution:** key prefix, the idiomatic Redis approach (logical DBs rejected: unsupported in Cluster, coarse, still collide in db 0). `RedisClient.build_key()` is already the single choke point for all maestro keys, including locks and SCAN patterns; it prepends `redis_key_prefix` from config. Resulting shape: `maestro:STATE:...`, `maestro:REGISTERED:...`, `maestro:ENTITY_LOCK:...`. APScheduler's `RedisJobStore` writes its own keys outside the choke point; pass `jobs_key=f"{prefix}:apscheduler.jobs"` and `run_times_key=f"{prefix}:apscheduler.run_times"`. Configurable prefix also enables multiple maestro instances on one Redis.

Related fix: `RegistryManager.redis_client = RedisClient()` is a class attribute instantiated at import time (reads config too early). Make it lazy (property or `get_config()`-time construction). Audit for other eagerly-constructed clients during the port.

## Packaging (hass-maestro)

- **Name**: check PyPI availability; `maestro` is almost certainly taken. Candidates: `hass-maestro`, `maestro-ha`. The import name can stay `maestro` regardless of distribution name.
- **Build**: hatchling (or uv build backend), package = `maestro/`, include `py.typed` (strict typing is a selling point).
- **pytest plugin**: entry point `[project.entry-points.pytest11] maestro = "maestro.testing.fixtures"` so the `mt` fixture auto-registers for consumers.
- **Dependency audit** against current pyproject:
  - Stay: apscheduler, aiohttp, flask, flask-sqlalchemy, sqlalchemy, redis, requests, structlog, python-dateutil, tzlocal (verify last two are actually used).
  - Move to maestro-scripts: `catt` (only used by `scripts/frontend/cast.py`), `gunicorn` (deployment concern).
  - Optional extra or user-owned: `psycopg` (DB driver is the user's choice; document `pip install hass-maestro[postgres]` or let users add their own driver).
- Carry over ruff/mypy config minus the per-file-ignores that belong to user-space code (registry, scripts tests).
- README targeting external users: quickstart, constructor reference, registry/custom-domains workflow, testing with `mt`.

## Build Order

Each phase ends verifiable. Library phases are verified by `uv run pytest maestro`, `uv run mypy maestro`, `uv run ruff check maestro`; the existing test suite (which never needed Redis or HA) should pass throughout.

1. **Seed hass-maestro**: copy framework package, drop `scripts/` coupling stubs, set up pyproject skeleton.
2. **Config objectification**: `MaestroConfig` + `get_config()`, convert the 12 modules, delete env reads. Largest mechanical change; do first since everything else reads config.
3. **MaestroApp**: constructor init sequence, `get_app()`, module-level `db`, optional DB, `background_services`, delete test/shell branching, parameterized `load_script_modules`.
4. **Registry + custom domains**: `registry_dir` / `custom_domains_dir`, dual-import generation, delete the wildcard graft.
5. **Redis prefixing**: `build_key` prefix, job store keys, lazy `RegistryManager.redis_client`.
6. **Packaging polish**: pytest entry point, py.typed, dependency audit, README, AGENTS.md rewrite for the new repo.
7. **Seed maestro-scripts**: copy scripts subrepo; write `app.py`; update imports (`from maestro.app import db` -> `from maestro import db`; `from maestro.registry.x import ...` -> `from registry.x import ...`; custom domain imports); move `catt`/`gunicorn`/driver deps; port Dockerfile/justfile (gunicorn target `maestro.app:app` -> `app:app`).
8. **End-to-end validation**: maestro-scripts test suite green, then deploy to the mac mini and soak. Registry regenerates into `registry/` on first run against live HA (or copy the existing generated modules and fix their imports).

## Resolved Decisions (2026-07-17)

- **Distribution name**: `hass-maestro` (verified available on PyPI; `maestro` is taken). Import name stays `maestro`.
- **Script module imports**: package-scoped (`scripts.family.ellie`). Project root goes on `sys.path`; the scripts dir is imported as a package named after `scripts_dir.name`. This matches the registry/custom_domains pattern (every configured dir is a top-level package under the project root), keeps existing `from scripts.common...` cross-imports working, and eliminates today's dual module identity (`family.ellie` + `scripts.family.ellie`) that forced `_get_qual_name`'s `removeprefix("scripts.")` dedup hack. The prefix strip may be kept for log/qual-name readability, derived from config.
- **Registry files**: migrated from the existing generated modules with imports rewritten (`from maestro.registry.x` -> `from registry.x`, custom domain imports), not regenerated from live HA. Tests pass offline before first deploy.
- **Repo history**: preserved. Both new repos are clones of their originals (`maestro` -> `hass-maestro`, `maestro/scripts` -> `maestro-scripts`), restructured in place.
